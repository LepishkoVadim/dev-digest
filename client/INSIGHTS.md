## 2026-08-24 — The FIRST runtime (value) import from the `@devdigest/shared` barrel needs webpack `extensionAlias` or the build fails "Can't resolve ./contracts/*.js"  [gotcha]
**Problem:** `import { ExpectedFindings } from "@devdigest/shared"` (a Zod *schema* — a runtime value, not a type) broke the Next build with `Module not found: Can't resolve './contracts/findings.js'` at `src/vendor/shared/index.ts`. Every one of the ~93 prior client imports from the barrel is `import type { … }`, which TypeScript **erases**, so webpack never had to resolve the barrel's re-exports. The vendored barrel is synced from the server, so its re-exports carry NodeNext `.js` specifiers over `.ts` sources; `tsc` (moduleResolution `Bundler`) and vitest map `.js`→`.ts` automatically, but **webpack does not** — which is why typecheck + tests stayed green while `pnpm build`/`pnpm dev` failed. **Decision:** added `webpack: (config) => { config.resolve.extensionAlias = { ".js": [".ts",".tsx",".js",".jsx"], ... }; return config }` to `client/next.config.mjs`. One resolver alias fixes the whole class (all current + future runtime barrel imports). Leaf-importing (`@devdigest/shared/contracts/knowledge`) works only for leaf files like `knowledge.ts` (imports zod only); it does NOT help for `eval-ci.ts`, which has runtime `.js` cross-imports (`./findings.js`, `./knowledge.js`) — so fix the resolver, not the import. **Why:** the failure is invisible to typecheck/vitest and only bites the webpack builder; the first person to `import` a value (not a type) from the barrel hits it. Evidence: `client/next.config.mjs` (webpack extensionAlias), `src/vendor/shared/index.ts` (`export * from './contracts/*.js'`).

## 2026-08-24 — "Tab doesn't open" after adding a new component + new i18n keys is usually a STALE dev server, not a code bug — restart before debugging  [gotcha]
**Problem:** The Agents → Evals tab repeatedly "didn't open" (blank) right after edits that added a new component (`OwnerEvalsPanel`) and new `messages/en/eval.json` keys — even though `pnpm typecheck`, a render smoke test (empty AND populated data, both owner kinds), and `pnpm build` (`✓ Compiled successfully`) all passed. **Decision:** when a route goes blank right after adding a new client component and/or new i18n JSON keys, first `pkill -f "bin/next dev"` → `rm -rf client/.next` → restart `pnpm dev`, then hard-refresh — before touching code. Confirm the route serves with `curl -s -o /dev/null -w "%{http_code}" localhost:3000/<route>` and watch the dev output for `✓ Compiled /<route>`. **Why:** Next dev HMR frequently fails to hot-swap a brand-new component or newly-loaded message namespace and keeps serving a stale/blank chunk for that route; nothing in typecheck/build/tests reproduces it because those don't use the long-lived dev server's in-memory state. Pairs with the 2026-07-31 next-intl-restart entry (same root cause for messages) — the restart also fixes new-component blanks. Chasing it as a render bug wastes a full loop.

## 2026-08-09 — Deep-linking a Smart Diff finding to its FindingCard reuses targetRunId + polls for data-finding-id (accordion opens async)  [working approach]
**Problem:** A Smart Diff finding badge/label must open the specific `FindingCard` on the Findings tab. But findings render inside per-run `ReviewRunAccordion`s that are **collapsed by default** (only the first opens), so a naive `querySelector('[data-finding-id]')` finds nothing. **Decision:** the badge/label carries the finding `id` (added to `DiffFinding`; `labelByLine` now returns the finding, not just severity) and calls `router.replace(?tab=findings&finding=<id>)`. `page.tsx` passes `?finding=` to `FindingsTab` as `focusFindingId`; an effect there (1) finds the review whose findings include that id, (2) clears an active `?severity=` filter if it would hide the run, (3) reuses the existing `targetRunId`/nonce mechanism to open+scroll that accordion, then (4) `requestAnimationFrame`-polls (≤30 frames) for `[data-finding-id="<id>"]`, scrollIntoView + a 1.6s box-shadow flash, and (5) calls back to clear the `?finding=` param. **Why:** the accordion opening is async state, so the card isn't in the DOM on the same tick — poll, don't assume. `FindingCard` already exposes `data-finding-id`; reuse it rather than inventing anchors. Clearing the param after focus stops the effect from re-firing (and avoids a loop). Evidence: `SmartDiffViewer.tsx` (goToFinding), `FindingsTab.tsx` (focus effect), `severity.ts` (labelByLine → DiffFinding).

## 2026-08-08 — A sticky panel inside a PR page hides behind PrDetailHeader (sticky top:0) unless you offset by its measured height  [gotcha]
**Problem:** Smart Diff's left `FileNav` is `position: sticky; top: 12`, but on scroll its search/filter header vanished. Cause: the PR detail page renders `PrDetailHeader` with `position: sticky; top: 0; zIndex: 5` and an **opaque** `background` inside the `<main overflow:auto>` scroller (`_components/PrDetailHeader/styles.ts`). A second sticky element in the same scroller with `top < header height` pins *underneath* it and is painted over. **Decision:** measure the header live and offset the nav by it. From the component root, `rootRef.current.closest("main")`, find the first child whose `getComputedStyle(el).position === "sticky"`, and set `navTop = header.offsetHeight + 12` (via `ResizeObserver`, because the header height changes — tabs, optional stale banner). Pass `navTop` as the nav's `top` and its `maxHeight: calc(100vh - navTop - 24px)`; also set each diff file wrapper's `scrollMarginTop: navTop` so "jump to file" clears the header too. Guard: `closest('main')` null (tests) or `ResizeObserver` undefined → bail to a 64px default. **Why:** hardcoding `top` is fragile (header height is dynamic); nested-sticky-behind-sticky is invisible in code review and only shows on scroll. Any sticky UI added to a PR/detail page must clear `PrDetailHeader`. Evidence: `SmartDiffViewer.tsx` (navTop effect), `PrDetailHeader/styles.ts`.

## 2026-08-08 — Smart Diff FileNav "scroll to file" needs the group's open-state lifted OR the anchor isn't in the DOM  [gotcha]
**Problem:** The left `FileNav` scrolls the diff to a file via `getElementById('sd-file-'+path)`. But `RoleGroup` only renders its files' cards (and their anchors) while the group is open, and **boilerplate is collapsed by default** — so clicking a boilerplate file in the nav found no element and silently did nothing. **Decision:** Lift group open-state out of `RoleGroup` into `SmartDiffViewer` (`openRoles: Set<SmartDiffRole>`, controlled `open`/`onToggle`). `selectFile(path)` looks up the file's role via a `roleByPath` map, adds it to `openRoles` if missing, THEN `requestAnimationFrame` → `scrollIntoView` (next frame, after the card mounts). Wrap each card in `<div id={fileAnchorId(path)} style={{scrollMarginTop}}>`. **Why:** any "jump to X" over collapsible content has this trap — the target must exist before you scroll. The rAF is load-bearing: expanding is a state update, so the anchor isn't in the DOM synchronously. Same shape as the finding-badge scroll in `FileCard` (which force-opens its own card first). Evidence: `SmartDiffViewer/{SmartDiffViewer,FileNav}.tsx`.

## 2026-08-08 — SmartDiffViewer: grouping from smart-diff, but badges/highlights come from the REVIEWS endpoint (severity)  [gotcha]
**Problem:** `GET /pulls/:id/smart-diff` returns `SmartDiffFile` with `finding_lines: number[]` and **no `patch`**. Two things bit me driving the UI off that alone: (1) `finding_lines` is a flat line list — no severity and no way to count *findings* (a badge built from it counts flagged lines, and a 3-line finding shows "3"); (2) it carries no patch to render. **Decision:** `SmartDiffViewer` uses smart-diff **only for grouping/order** and pulls the actual findings from `usePrReviews(prId)` (`GET /pulls/:id/reviews`), whose `FindingRecord`s carry `file`/`start_line`/`end_line`/`severity`. It builds a `Map<path, DiffFinding[]>` and passes it to `FileCard`; the badge counts `findings.length` and is coloured by the top severity, and each finding line is tinted + labelled by its own severity via `severityByLine`/`labelByLine` (`components/diff-viewer/severity.ts`, folding overlaps to the most severe). Patch comes from joining the `PrFile[]` `DiffTab` already has, by `path`. `FileCard`/`CodeLine` gained *optional* `findings`/`severity`/`severityLabel`/`anchorId` props (additive — the plain `DiffViewer` path is unchanged). Colours/icons/labels reuse the canonical `SEV` map from `@devdigest/ui` (`--crit/--warn/--sugg`); the per-line label text is `diffViewer.sev.*` = blocker/warning/suggestion to match the design. **Why:** the assignment literally says the reviews endpoint (with severity) is what drives "badges, line highlighting and auto-expansion" — `finding_lines` can't express severity or a finding count. Invalidate `["smart-diff", prId]` alongside `["reviews", prId]` in every review mutation or badges go stale after Run Review. Evidence: `components/diff-viewer/{SmartDiffViewer,FileCard,CodeLine,severity}`.

## 2026-08-08 — `src/lib/feature-models.ts` is a hand-mirror of a server runtime value that NO CI gate covers  [gotcha]
**Problem:** `client/src/lib/feature-models.ts` mirrors the `FEATURE_MODELS` array from `server/src/vendor/shared/contracts/platform.ts`, but `./scripts/sync-shared.sh` (and `contracts-sync.yml`) only cover `vendor/shared` — this file is under `lib/`, so it drifted with **zero** CI failure (`conventions` said `openai/gpt-5.4` while the server said `openrouter/deepseek-v4-flash`). **Decision:** Whenever `FEATURE_MODELS` changes on the server, hand-edit this mirror to match entry-for-entry and eyeball it (`id`/`label`/`description`/`defaultProvider`/`defaultModel`, including the U+2019 apostrophe in "PR’s"). It is a mirror of a runtime *value*, not a type, so the client cannot import it (see the file's own header comment). **Why:** Unlike the `vendor/shared` drift, nothing fails the PR here — the Settings model picker just renders a wrong default silently. Distinct from the 2026-08-01 `vendor/ui` entry: that dir has no upstream at all; this one *does* have an upstream (`platform.ts`) that the sync script simply does not reach.

## 2026-08-08 — Shared contracts: never hand-copy the mirror — edit the source and run sync-shared.sh  [gotcha]
**Problem:** The client didn't see a contract field added on the server. The vendored client copy is what the app validates against, so a one-sided edit drops the field with no error. **Decision:** Never hand-copy `client/src/vendor/shared/**`. Edit the source at `server/src/vendor/shared/contracts/*`, then run `./scripts/sync-shared.sh`, and commit both copies. Verify with `./scripts/sync-shared.sh --check` (exit non-zero = mirror stale). **Why:** `.github/workflows/contracts-sync.yml` runs `./scripts/sync-shared.sh --check` on every PR — a hand-copy that differs by a byte now fails CI instead of passing quietly. Note the still-true carve-out in the 2026-08-01 entry: this covers `vendor/shared` only; `vendor/ui` has no upstream source and is still edited directly. Evidence: `scripts/sync-shared.sh:19` (`--check` mode), `.github/workflows/contracts-sync.yml`.

That text was removed rather than left superseded-in-place, because `.claude/settings.json`'s `UserPromptSubmit` hook cats this whole file into any prompt mentioning `client` — a stale claim here is not inert, agents read it as current. ## 2026-07-31 — Hover popover that lazy-loads: mount content only while open
**Problem:** A hover popover on every PR-list row must show finding details, but fetching all rows' findings upfront is wasteful. **Decision:** `HoverCard` (pulls/_components/HoverCard) renders its content **only while `open`**; the list popover content (`ListFindingsPreview`) calls `usePrReviews(prId)` and thus fires the request only when the card mounts (on hover). **Why:** No `enabled` flag or hook changes needed — mount-gating is the trigger. TanStack caches by `["reviews", prId]`, so re-hover is instant. There is no Popover/Tooltip/HoverCard primitive in `@devdigest/ui`, so this small component fills the gap.

## 2026-07-31 — PR-detail findings are grouped per run; PR-wide filters live in FindingsTab
**Problem:** A PR-wide severity filter/tally has no single findings list to hook into — findings render per review run (`FindingsTab` → `ReviewRunAccordion` → `FindingsPanel`, one panel per run). **Decision:** Lift the aggregate (counts from `reviews.flatMap(r => r.findings)`) and the active-filter state to `FindingsTab`, thread `severityFilter` down into every `FindingsPanel`, and hide accordions with zero matches. **Why:** Matches how the detail page already fans findings across runs; computing counts from the already-fetched reviews keeps them consistent with what's rendered and needs zero extra requests.

## 2026-07-31 — next-intl keys need a dev restart + hard refresh to appear
**Problem:** A newly-added message key rendered as its raw path (e.g. `runs.trace.stat.cost`) even though the JSON was correct. **Decision:** After editing `messages/en/*.json`, restart the web dev server and hard-refresh. **Why:** `src/i18n/request.ts` reads messages via fs and they're hydrated into `NextIntlClientProvider` at page load; client-side navigation reuses the stale hydrated set, so a missing key falls back to the dotted path until a fresh server render.

## 2026-08-01 — @devdigest/ui (incl. nav.ts) is vendored but NOT synced — edit it directly
**Problem:** Adding a sidebar entry (Skills) meant editing `src/vendor/ui/nav.ts`, but `src/vendor/*` is flagged do-not-touch. **Decision:** Add nav entries directly in `client/src/vendor/ui/nav.ts` (the `NAV` array + `SHORTCUTS`). **Why:** `scripts/sync-shared.sh` only mirrors `@devdigest/shared` (server→client); there is NO upstream source for `@devdigest/ui` and no CI check over it — the vendored `ui/` dir IS the de-facto source. The `activeKeyFor()` highlight logic already handles `/skills`, but the visible sidebar link only exists once it's in `NAV`. (The do-not-touch rule is really about `shared`, which contracts-sync CI enforces.)

## 2026-08-01 — recharts chart files MUST carry "use client" or dev RSC crashes
**Problem:** `/`, `/agents` (any route using `app/loading.tsx`) threw `TypeError: Super expression must either be null or a function` at `vendor/ui/charts/LineChart.tsx` — but ONLY in `pnpm dev`, never in `pnpm build`. **Decision:** Every chart file importing `recharts` (`vendor/ui/charts/LineChart.tsx`, `Donut.tsx`) must start with `"use client";`. **Why:** `loading.tsx` (a Server Component) imports `Skeleton` from the `@devdigest/ui` barrel; in dev the barrel is NOT tree-shaken, so `charts/index.ts` → recharts gets evaluated in the RSC/server graph, and recharts' class components fail `class extends <undefined>` under RSC. Prod hides it because tree-shaking drops the unused charts from that server module. The `"use client"` boundary keeps recharts out of the server graph entirely.

## 2026-08-09 — "Blast tab" in the spec was really an Overview CARD — the i18n keys were the tell
**Problem:** The Blast Radius spec literally said "add a Blast tab", so it was first built as a standalone `_components/BlastTab` + a 4th tab in `PrDetailHeader`. That was wrong: the design (and the reviewer's screenshot) puts BLAST RADIUS as a **card in the Overview**, next to Intent — there is no Blast tab. **Decision:** Render it via `_components/BlastCard`, placed in `OverviewTab` in a 2-col grid beside `IntentCard`; do NOT add a tab. **Why / the tell:** `client/messages/en/blast.json` already existed with `stat.symbols/callers/endpoints/crons`, `view.tree/graph`, `callerCount`, `graph.empty` — i.e. the design for an Overview tree/graph card was pre-staged. **Check pre-existing i18n namespaces + design assets before choosing UI placement**, and prefer the existing card pattern (`<section><SectionLabel/><div style={s.card}>…`, see `IntentCard`) over a new tab when a matching `messages/en/<feature>.json` already exists. Second footgun: a Blast card can list 90+ changed symbols — rank them server-side by importance (most callers first; `blast/service.ts::compareSymbolImportance`) and show only the top N inline, the rest behind a `@devdigest/ui` `Modal` ("See all"); compute the header stat totals over ALL symbols, not the visible slice.

## 2026-08-23 — Moving/renaming an App Router route makes `pnpm typecheck` fail on STALE `.next/types`, not your code  [gotcha]
**Problem:** After `git mv`-ing a route (`app/project-context/` → `app/repos/[repoId]/project-context/`), `pnpm typecheck` failed with `.next/types/app/project-context/page.ts … error TS2307: Cannot find module '../../../../src/app/project-context/page.js'`. The error points at a **generated build artifact for the OLD path**, not any source file you touched — easy to misread as a broken import in your move. **Decision:** After moving, renaming, or deleting any `app/**/page.tsx|layout.tsx` route, `rm -rf client/.next` (or rebuild) before typechecking — Next regenerates `.next/types/app/**` from the current route tree and the phantom error disappears. `tsconfig` pulls in `.next/types/**/*.ts`, so `tsc` reads those stale per-route type shims. **Why:** the type files are keyed by route path; a moved route leaves an orphan whose relative `import('../../../../src/app/<old>/page.js')` now resolves to nothing, and nothing invalidates it until a Next build re-runs. Before editing source to "fix" it, check the failing path is under `.next/` — if so it's a stale artifact, not your bug.
