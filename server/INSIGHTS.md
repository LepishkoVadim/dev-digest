## 2026-08-09 — RepoIntelService.getBlastRadius already works; only the HTTP route is missing  [gotcha]
**Problem:** Planning a consumer of "blast radius" (e.g. an MCP tool) it's easy to assume the feature doesn't exist yet and needs building from scratch — `repo-intel/routes.ts` exposes only `/index-state` and `/resync`, no blast endpoint. **Decision:** The logic already exists — `RepoIntelService.getBlastRadius` (`server/src/modules/repo-intel/service.ts:212`) is a working facade, already consumed internally (e.g. `reviews/run-executor.ts:479`'s high-blast-risk prompt note). Exposing it externally is "add a route", not "implement blast radius". **Why:** Saves re-deriving/duplicating logic that's a facade call away; the real gap is route wiring only.

## 2026-08-09 — Server has no auth; workspaceId is always server-resolved, never client-supplied  [gotcha]
**Problem:** Routes reference `workspaceId` everywhere (`getContext(container, req)`), which reads as per-request tenancy resolved from the caller. A new HTTP client (e.g. an MCP server) can wrongly conclude it must compute/pass a workspace id. **Decision:** `LocalNoAuthProvider` (`server/src/adapters/auth/local.ts:14-37`) always resolves the same seeded system user + default workspace regardless of request contents; `getContext()` (`server/src/modules/_shared/context.ts:14-23`) never reads a workspace id from the request, and no route accepts one as a param. A local client needs only repo/PR/agent identifiers — building workspace-id plumbing on the client side is dead code today. **Why:** `workspaceId` in signatures is forward-compatible naming for future multi-tenancy, not a currently-enforced boundary; don't build for the enforcement that isn't there yet.

## 2026-08-08 — Smart Diff route queries findings INLINE (not via the reviews repo) to avoid a NEW arch violation  [gotcha]
**Problem:** `GET /pulls/:id/smart-diff` (pulls module) needs the latest review's findings. The obvious move — `import { reviewsForPull } from '../reviews/repository/review.repo.js'` — typechecks and works, but adds a **new** `no-cross-module-internals` edge (`pulls/routes.ts → reviews/repository/review.repo.ts`). The sibling `run.repo` import is in `.dependency-cruiser-known-violations.json`; `review.repo` is NOT, so it's a fresh violation. **Decision:** Query findings inline with Drizzle in the route — `select(...).from(t.findings).innerJoin(t.reviews, ...).where(and(eq(prId), eq(kind,'review')))` — exactly the pattern the PR-list block already uses (see the 2026-07-31 "on-read, one IN-query" entry). The `pulls/routes.ts → db/schema.ts` (`no-route-to-db`) edge this relies on is already baselined, so the arch count stays at 13. **Why:** `arch:check` isn't a CI gate (not in any workflow), but the architecture-reviewer agent runs `depcruise --ignore-known` and a new edge would surface. Cross-module data access in this repo goes through inline Drizzle in the owning module's route, not by importing another module's repository. Smart Diff also makes NO LLM call, so its `.it.test.ts` needs no provider stub (the live-call trap in the entry below doesn't apply). Evidence: `test/smart-diff.it.test.ts`, `modules/pulls/routes.ts` smart-diff handler.

## 2026-08-08 — A `.it.test.ts` that leaves a provider unstubbed makes LIVE, billed OpenRouter calls  [gotcha]
**Problem:** Adding a shared pre-work LLM step to `reviews/run-executor.ts` (intent classification, which resolves `review_intent` → `openrouter`) silently broke and slowed the existing DB-backed review tests: `container.llm(id)` falls back to the real key in `~/.devdigest/secrets.json` for any provider the test did not inject via `overrides.llm`, so the "new" provider hit the real API. The map-reduce test began asserting against genuine model output and the suite went 14s → 45s, with real spend. **Decision:** When a code path under `.it.test.ts` gains a *new* provider/feature-model, add that provider to the test's `overrides.llm` (a `MockLLMProvider` keyed by `schemaName`, e.g. `'Intent'`) in `server/test/reviews.it.test.ts`. To test "the LLM call fails", inject a provider that returns schema-invalid output — **never** rely on leaving it unstubbed. **Why:** No test harness blocks outbound network by default, and the container's secret fallback is invisible at the call site, so an unstubbed provider looks like it "just works" while quietly billing and flaking. Injecting no provider is not failure-injection; it is a live call.

## 2026-08-08 — Intent confidence is computed in code from source presence, never self-reported by the model
**Problem:** The intent classifier could return its own `confidence`, but LLM self-reported confidence tracks commitment, not correctness (arXiv:2606.29490 / 2606.03437 — surfaced in the design research). **Decision:** `IntentResult` (the model's schema in `reviews/intent.ts`) returns only `{ intent, in_scope[], out_of_scope[] }`. `deriveConfidence(sources)` maps the deterministic source inventory → `high|medium|low`; any `unavailable` source forces `low`. Same "model proposes, code disposes" shape as the conventions evidence gate. **Why:** The gate is what makes the confidence signal trustworthy and un-gameable by a malicious PR body. An `unavailable` linked-issue/spec link must lower confidence and appear in the prompt's `## Missing context` — a silent gap or a model-invented value is exactly the failure the feature exists to prevent. `hunkHeaderDigest` is the single bridge from the diff and reads positional fields only (`intent.test.ts` asserts no `+`/`-` line and no diff body leaks into the classifier).

## 2026-08-08 — SUPERSEDES the 2026-07-31 "no sync script" entry: sync-shared.sh exists and CI enforces it  [gotcha]
**Problem:** The 2026-07-31 entry directly below ("Shared contracts have no sync script; edit source AND mirror") is now **false**, and it actively misleads: `.claude/settings.json`'s `UserPromptSubmit` hook injects this file into any prompt mentioning `server`, so agents read it as current and hand-mirror the client copy. **Decision:** Edit only the source under `server/src/vendor/shared/contracts/*`, then run `./scripts/sync-shared.sh` and commit both copies. Never hand-edit `client/src/vendor/shared/**`. Check staleness with `./scripts/sync-shared.sh --check`. **Why:** The script landed after that entry was written and `.github/workflows/contracts-sync.yml` runs it in `--check` mode on every PR, so drift now fails the PR rather than failing silently at runtime. The *mechanism* the old entry describes is still correct — fastify's zod serializer strips keys not in the schema — only its "there is no script" premise is wrong. Evidence: `scripts/sync-shared.sh:19`, `.github/workflows/contracts-sync.yml`.

## 2026-07-31 — Shared contracts have no sync script; edit source AND mirror
**Problem:** Adding a field to a `@devdigest/shared` Zod contract (e.g. `PrMeta.cost_usd`, `PrMeta.findings_counts`) only in `server/src/vendor/shared` silently drops it from the client. **Decision:** Always edit the source copy under `server/src/vendor/shared/contracts/*` AND hand-mirror the identical change into `client/src/vendor/shared/contracts/*`. **Why:** There is no vendor-sync script. The server route may return the field, but fastify's zod serializer strips keys not in the schema, and the client's vendored zod won't expose them — so a one-sided edit fails quietly with no type error.

## 2026-07-31 — PR-list per-PR aggregates are computed on-read, one IN-query each
**Problem:** Where to add a new per-PR column (SCORE, COST, FINDINGS) on `GET /repos/:id/pulls`. **Decision:** Follow the existing block in `modules/pulls/routes.ts`: collect `prIds`, run ONE `inArray(...)` query per metric, group in JS into a `Map<prId, …>`, then read it in the final `rows.map`. No FK denormalization. **Why:** The list is small; on-read keeps the schema clean and avoids write-path coupling. Use `null` (not `0`) when a PR has no data so the UI renders "—".

## 2026-08-01 — Skills reach the prompt via run-executor, filtered + wrapped
**Problem:** Where do a skill's contents actually enter an agent's review, and how is an untrusted (imported) skill kept from acting as an instruction? **Decision:** `reviews/run-executor.ts::runOneAgent` loads `agentsRepo.linkedSkills(agentId)` and passes them through the pure `resolveSkillBlocks()` helper (`reviews/helpers.ts`) into `reviewPullRequest({ skills })`. `resolveSkillBlocks` drops skills whose global `enabled` is false, emits `manual`-source bodies raw, and wraps every non-`manual` body in `wrapUntrusted('skill:'+name, …)` (exported by `@devdigest/reviewer-core`). **Why:** The skills module owns CRUD only; the agent↔skill link + prompt assembly is owned by agents/reviews. Filtering on `enabled` is the "disabled until vetted" gate — an unvetted import literally cannot reach a prompt. The `<untrusted>` wrap is what makes "someone else's skill = someone else's instructions" safe; `assemblePrompt` already renders the block + records it in the run trace.

## 2026-08-01 — Conventions Extractor: model proposes, code disposes
**Problem:** How to make extracted conventions trustworthy enough to become a skill. **Decision:** `modules/conventions` runs a 4-step pipeline — sample (pure code: `CONFIG_PATHS` + `repoIntel.getConventionSamples`, read via `git.readFile`) → cheap LLM (`resolveFeatureModel(ws,'conventions')`, now `openrouter/deepseek-v4-flash`) → **code-side evidence gate** (`helpers.verifySnippet`: the model's snippet must actually exist in the file; drops it otherwise and pins the verified 1-based line) → persist. Only the LLM step is non-deterministic; sampling + the gate are pure and unit-tested (`helpers.test.ts`). Accepted candidates merge into ONE `extracted`/`convention` skill via `SkillsRepository.insert` (reused, not reimplemented), optionally linked to an agent. **Why:** A model citing `file:line` is worthless unless verified — the gate is what lets "clickable evidence → real code" hold and keeps hallucinated rules out of the skill. `evidence_line` (new nullable col) is computed by the gate, not trusted from the model. Re-scan keeps accepted rows (`replaceUnaccepted`) so a re-run never discards a kept rule.
